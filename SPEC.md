# Спецификация — Notes API

## Что делаем

HTTP-API для заметок с тегами: полный CRUD, фильтрация по тегам и аналитика по частоте
тегов. Хранилище — один JSON-файл, без базы данных.

## Для кого и зачем

Учебный сервис для домашнего задания курса. Пользователь API — клиент, который ведёт
короткие заметки и разбирает их тегами. Задача, которую решает сервис: найти заметку
по сочетанию тегов и увидеть, какими тегами человек пользуется чаще всего.

Настоящая цель проекта — не заметки, а проверяемое поведение: у каждого запроса есть
заранее описанный ожидаемый ответ, с которым сверяется факт.

## Сценарии

1. Клиент создаёт заметку с заголовком, текстом и тегами → получает `201` и созданную
   заметку с присвоенным `id` и нормализованными тегами.
2. Клиент запрашивает список заметок с фильтром по тегам → получает `200` и массив
   подходящих заметок.
3. Клиент читает одну заметку по `id` → получает `200` и заметку.
4. Клиент полностью заменяет заметку через `PUT` → получает `200` и новое состояние.
5. Клиент удаляет заметку → получает `204` без тела.
6. Клиент запрашивает топ тегов → получает `200` и список пар «тег — сколько заметок».

Ненормальные сценарии:

7. Клиент прислал тег из одних пробелов → `422`, в теле указан индекс проблемного тега.
8. Клиент прислал поле, которого нет в схеме → `422`, в теле названо лишнее поле.
9. Клиент обратился к несуществующему `id` → `404`.
10. Клиент отправил тот же `PUT` дважды → второй раз тот же `200` и то же тело,
    `updatedAt` не изменился.
11. Файл хранилища испорчен → `500` с кодом `STORAGE_CORRUPTED`, без трассировки стека,
    запись не выполняется.

## Состояния

| Состояние | Что видит клиент |
|---|---|
| Файла хранилища нет | Список пуст (`200`, `[]`). Файл создаётся при первой записи |
| Файл есть, пустой (`0` байт) | Список пуст (`200`, `[]`). Равнозначно отсутствию файла |
| Файл есть, в нём `[]` | Список пуст (`200`, `[]`) |
| Есть данные | Список заполнен |
| Фильтр не дал совпадений | `200` и пустой массив. Это не ошибка |
| Файл испорчен на верхнем уровне (не JSON, не список) | `500` `STORAGE_CORRUPTED`. Чтение и запись отказывают, данные не затираются |
| Файл — список, но хотя бы одна запись не той формы | То же самое: `500` `STORAGE_CORRUPTED` на чтении **и на записи**. `POST` и `DELETE` отклоняются, а не пишут поверх |
| Путь существует, но это не файл (например, каталог) | `500` `STORAGE_FAILURE`. Сломанное хранилище не выдаётся за пустое |
| Запрошен несуществующий маршрут | `404` `ROUTE_NOT_FOUND` |
| Запрошен несуществующий `id` | `404` `NOTE_NOT_FOUND` |
| Тело не прошло валидацию | `422` `VALIDATION_ERROR` с перечнем полей |
| Тело — не валидный JSON | `400` `BAD_REQUEST` |
| Метод не поддержан на этом пути | `405` `METHOD_NOT_ALLOWED` |

## Контракт API

Базовый путь: `/api/v1`. Тело запроса и ответа — `application/json; charset=utf-8`.

### Формат ответа

Успех:

```json
{ "success": true, "data": { } }
```

`data` всегда объект, никогда массив верхнего уровня. Списки лежат внутри под ключом
`items`: `{"success": true, "data": {"items": [...]}}`. Так добавление соседнего поля
(например, `total`) не ломает клиентов.

Ошибка — единый формат для всех кодов:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Переданные данные не прошли проверку",
    "fields": { "tags.1": ["Тег не может быть пустым"] }
  }
}
```

Полный перечень значений `error.code`: `VALIDATION_ERROR` (422), `BAD_REQUEST` (400),
`NOTE_NOT_FOUND` (404), `ROUTE_NOT_FOUND` (404), `METHOD_NOT_ALLOWED` (405),
`STORAGE_CORRUPTED` (500), `STORAGE_FAILURE` (500), `INTERNAL_ERROR` (500).
Других значений сервис не отдаёт.

`fields` присутствует только у `422` и всегда является JSON-объектом, даже если все
имена полей состоят из цифр. Ключ — имя поля ровно в том виде, в каком его прислал клиент.

Трассировки стека, абсолютные пути и текст внутренних исключений наружу не уходят никогда,
в том числе при `500`. PHP-предупреждения перехватываются и не попадают в тело ответа:
без этого warning печатался бы до отправки заголовков, и клиент получил бы `200 OK`
с `Content-Type: text/html`.

### Модель заметки

```json
{
  "id": "0f3a1c6e-6a2b-4b7f-9c3d-2f1e8a5b4c70",
  "title": "Созвон с командой",
  "content": "Обсудить сроки релиза",
  "tags": ["РАБОТА", "СРОЧНОЕ"],
  "createdAt": "2026-08-17T18:42:11+00:00",
  "updatedAt": "2026-08-17T18:42:11+00:00"
}
```

- `id` — UUID v4, назначает сервер. Присланный клиентом `id` — лишнее поле → `422`.
- `createdAt` / `updatedAt` — ISO-8601, всегда UTC. Назначает сервер.

### Правила поля `tags`

Решение зафиксировано человеком, а не выбрано агентом:

1. `trim` по краям каждого тега.
2. Приведение к **верхнему регистру** через `mb_strtoupper` (UTF-8, кириллица работает).
3. Дедупликация **после** нормализации, порядок первого вхождения сохраняется.

Пример: `["  Работа ", "работа", "Work"]` → `["РАБОТА", "WORK"]`.

- Тег, ставший пустым после `trim`, — ошибка `422` с индексом (`tags.2`), а не молчаливое
  выбрасывание. Молча съеденный элемент массива — это потеря данных клиента.
- Ограничения: длина тега 1–32 символа после нормализации, до 10 тегов на заметку.
- `tags` можно не присылать или прислать `[]` — заметка без тегов допустима.

### Эндпоинты

| Метод | Путь | Успех | Ошибки |
|---|---|---|---|
| `POST` | `/api/v1/notes` | `201` | `400`, `422` |
| `GET` | `/api/v1/notes` | `200` | `422` |
| `GET` | `/api/v1/notes/{id}` | `200` | `404` |
| `PUT` | `/api/v1/notes/{id}` | `200` | `400`, `404`, `422` |
| `DELETE` | `/api/v1/notes/{id}` | `204` | `404` |
| `GET` | `/api/v1/tags/top` | `200` | `422` |

Дополнительно на **любом** пути: `405`, если путь существует, но метод не поддержан,
и `500` `STORAGE_CORRUPTED`, если файл хранилища повреждён. В таблице они не повторяются,
потому что не зависят от конкретного эндпоинта.

Порядок проверок на `PUT`: сначала разбор тела (`400`), затем валидация полей (`422`),
и только потом поиск заметки (`404`). То есть `PUT` по несуществующему `id` с лишним
полем в теле вернёт `422`, а не `404`: тело разбирается до обращения к хранилищу.

#### `POST /api/v1/notes`

Тело: `title` (обязательно, строка, 1–200), `content` (необязательно, строка, до 10000,
по умолчанию `""`), `tags` (необязательно, массив строк).

Любое поле сверх этих трёх → `422` с именем лишнего поля. Решение принято осознанно:
опечатка в имени поля ловится сразу, а не превращается в «почему моё поле не сохранилось».
Цена — расширение схемы становится ломающим изменением для старых клиентов;
для учебного сервиса это приемлемо.

#### `GET /api/v1/notes`

Параметры запроса:

- `tags` — список тегов через запятую. Нормализуется теми же правилами, что и при записи,
  поэтому `?tags=работа` находит заметку с тегом `РАБОТА`.
- `mode` — `all` (по умолчанию) или `any`. `all` — заметка содержит **все** перечисленные
  теги; `any` — хотя бы один. Любое другое значение → `422`.

Неизвестный тег в фильтре — не ошибка: `200` и пустой `items`. Тег не является справочной
сущностью, у него нет отдельного жизненного цикла, поэтому «такого тега нет» неотличимо
от «по нему ничего не нашлось».

Пустой сегмент в списке (`?tags=работа,,дом`) — ошибка `422` с индексом (`tags.1`),
как и пустой тег в теле. Правило одно и то же в обоих местах: молча выбросить пустой
элемент значит принять решение за клиента. Отсутствующий или пустой параметр
`?tags=` — это отсутствие фильтра, а не пустой сегмент.

Сортировка: `createdAt` по убыванию, при равенстве — по `id` по возрастанию.
Тай-брейк задан явно, чтобы порядок был воспроизводим в тестах.

#### `PUT /api/v1/notes/{id}`

Полная замена. Тело то же, что у `POST`. Непереданные необязательные поля сбрасываются
в значения по умолчанию — это замена, а не правка.

Идемпотентность: повторная отправка того же тела возвращает `200` и то же самое тело,
`updatedAt` **не меняется**, если результат нормализации совпал с текущим состоянием.
Выбрана идемпотентность, а не `409`: ретраи по таймауту у любого сетевого клиента
неизбежны, и второй ретрай не должен выглядеть как ошибка.

Несуществующий `id` → `404`. `PUT` не создаёт заметку по указанному клиентом `id`,
потому что `id` назначает только сервер.

#### `DELETE /api/v1/notes/{id}`

`204` без тела. Повторное удаление → `404`: удаление не идемпотентно по коду ответа
осознанно, клиенту полезно знать, что он удалил не то, что думал.

#### `GET /api/v1/tags/top`

Параметр `limit` — целое `1..100`, по умолчанию `10`. Значение вне границ или не число → `422`.

Ответ:

```json
{ "success": true, "data": { "items": [ { "tag": "РАБОТА", "count": 12 } ] } }
```

`count` — число заметок с этим тегом, не число упоминаний: внутри одной заметки теги
уже дедуплицированы. Сортировка: `count` по убыванию, при равенстве — `tag` по алфавиту
по возрастанию. Тай-брейк задан явно: без него порядок зависит от порядка записей в файле
и тест становится плавающим.

Заметок нет → `200` и пустой `items`.

## Архитектура

Слои и направление зависимостей взяты из плагина `laravel-arch`, **без самого Laravel**:

```
Controller → Interfaces\Services → Interfaces\Repositories → JSON-файл
     ↓              ↓
  Request         DTO, Support\Helpers, Exceptions\System
  Resource
```

Что переносится дословно: разделение слоёв, контракты в `Interfaces/`, DTO с `readonly`
и суффиксом `Dto`, контракт чтения `get*` / `find*` / `exists*` / список-возвращает-`[]`,
исключения со своим HTTP-кодом через `ExceptionStatusCodeEnum`, отсутствие `try/catch`
в контроллере, `match` вместо лестниц `if`, поведение енама внутри енама, `readonly class`
для сервисов и репозиториев, именованные аргументы, явные типы возврата.

Что заменяется аналогом, потому что фреймворка нет:

| В плагине | Здесь |
|---|---|
| `FormRequest` | `Http/Requests/*Request` — собирает DTO из запроса методом `toDto()`; правила живут в `Validation/Rules` и `Validation/Validators` |
| `JsonResource` | `Http/Resources/*Resource` — маппер DTO → массив |
| Биндинги в `AppServiceProvider` | Свой минимальный контейнер `Support\Container` |
| Eloquent-модель | JSON-файл, видит его **только** репозиторий |
| `DatabaseHelper::transaction` | `Support\Helpers\File\JsonStorageHelper` — атомарная запись через временный файл и `rename`. Аналогия неполная: rollback-семантики нет, атомарность даёт сама операция `rename` |
| `LockHelper` через `Cache::lock` | `Support\Helpers\Lock\LockHelper` через `flock` |
| Рендер исключения в `bootstrap/app.php` | `Support\Http\ExceptionRenderer` — отдельный класс, вызываемый из `bootstrap/app.php`. Вынесен ради проверяемости: замыкание внутри сборки нельзя было покрыть тестом |

Ключевое правило сохранено: **репозиторий — единственный слой, который знает, где лежат
данные**. Замена файла на БД должна быть правкой одного слоя. Если для неё придётся
трогать сервис — слои разведены неправильно.

## Чего точно не делаем

- Базы данных, Redis, очередей, внешних сервисов. Хранилище — файл, это условие задания.
- Аутентификации и авторизации. Заметки общие, владельца у них нет.
- Пагинации (`limit` / `offset`) в списке заметок. Соблазн есть, но это отдельный класс
  пограничных случаев, а объём уже расширен аналитикой.
- Полнотекстового поиска по `title` и `content`. Фильтр только по тегам.
- Категорий и синонимов тегов (`работа` и `work` → категория `WORK`). Обсуждалось,
  вынесено в открытые вопросы.
- Мягкого удаления и корзины. `DELETE` удаляет запись.
- Версионирования API дальше префикса `/v1`.
- Генерации OpenAPI. В плагине это атрибуты `#[OA\...]` фреймворка, здесь их источника нет;
  контракт живёт в этом файле.
- Фронтенда. Проверка — через HTTP-клиент и тесты.

## Допущения

- **Длина тега 1–32 символа, до 10 тегов на заметку.** Границы не обсуждались, взяты
  как разумные; вынесены в константы, меняются одной строкой.
- **`title` 1–200 символов, `content` до 10000.** Тот же статус.
- **`id` — UUID v4, генерирует сервер.** Автоинкремент отвергнут: он течёт из хранилища
  наружу и мешает заменить файл на что-то другое.
- **Время всегда UTC.** Часовые пояса в задаче не участвуют, приводить их — лишний
  источник ошибок.
- **Конкурентность.** Каждая операция записи держит `flock` на отдельном lock-файле
  во временном каталоге, общем для всего приложения, а не на самом файле данных.
  Ключ блокировки — константа, он не зависит от пути хранилища: два экземпляра
  с разными файлами будут сериализоваться друг об друга. Это избыточная блокировка,
  а не некорректность.
  Для учебного сервиса этого достаточно; на нагрузке это узкое место, и это осознанно.
- **Испорченный файл не чинится автоматически.** Сервис отвечает `500` и отказывается
  писать. Альтернатива — молча пересоздать файл — отвергнута: это потеря данных
  под видом устойчивости.
- **`title` молча триммится**, и длина 1–200 меряется уже после trim. Для тегов молчаливая
  правка запрещена (пустой тег — ошибка), для `title` она допущена: пробелы по краям
  заголовка не несут смысла, а отказ на них раздражал бы клиента. Асимметрия осознанная.
- **Явный `null` в `content` и `tags`** равнозначен отсутствию поля и даёт значения
  по умолчанию (`""` и `[]`); `null` в `title` — ошибка, потому что поле обязательно.
- **Сортировка тегов по алфавиту** — побайтовая, без учёта локали. Латиница идёт перед
  кириллицей, `Ё` перед `А`. Для воспроизводимости этого достаточно; человеческая
  коллация потребовала бы `intl`, а зависимостей у проекта нет.
- **Ограничения длины и количества к тегам фильтра не применяются** — фильтр не создаёт
  данные, а слишком длинный тег просто ничего не найдёт.
- **Неизвестные параметры строки запроса игнорируются**, в отличие от полей тела.
  Тело — это данные, которые сохранятся; строка запроса — способ спросить.

## Как запускается PHP

Запрет задания — «не подключать базу данных, Docker и внешние сервисы: хранилище —
файл» — относится к тому, от чего зависит **продукт**. У продукта зависимостей нет:

- в репозитории нет ни `Dockerfile`, ни `docker-compose.yml`; Docker не является
  частью проекта и нигде в коде не упоминается;
- нет Composer, нет `vendor/`, нет ни одного пакета; автозагрузка своя;
- хранилище — JSON-файл, ни базы, ни кэша, ни очередей, ни сетевых вызовов;
- тестовый фреймворк — один `phar` в репозитории.

PHP и Composer на машине разработчика отсутствуют, ставить их локально владелец
проекта не хочет. Поэтому интерпретатор вызывается через контейнер `php:8.4-cli` —
это способ запустить `php`, а не компонент архитектуры. Тот же проект запускается
командой `php -S 0.0.0.0:8080 -t public public/index.php` на любом локальном PHP 8.4;
оба способа приведены в `README.md`.

**Это не проблема, не ограничение и не компромисс.** Контейнер заменяет собой
`brew install php`, и ничего кроме. Убрать его из процесса можно в любой момент,
не тронув ни строчки кода: удалить нечего — в проекте его нет.
В разделе «Известные проблемы» `STATE.md` он поэтому не значится.

## Открытые вопросы

1. **Категории тегов.** Прозвучало: в будущем `работа`, `work` и подобные должны сводиться
   к категории `WORK`. Это словарь синонимов и отдельная сущность. В текущий объём
   не входит, но нормализация тегов в верхний регистр выбрана в том числе с расчётом
   на это: `WORK` уже готовый вид ключа категории.
   Что нужно решить до реализации категорий: словарь ведёт человек или он выводится
   из данных; что делать с тегом, попавшим в две категории.
2. **Границы длин** (`32`, `10`, `200`, `10000`) приняты агентом как допущение
   и требуют подтверждения человеком.
3. **Поведение при одновременной записи двух процессов** проверено только логикой `flock`,
   нагрузочного теста не будет — это за границей объёма.

## Критерии приёмки

- [x] Сервис поднимается одной командой из `README.md` и отвечает на `GET /api/v1/notes`
      кодом `200` на пустом хранилище.
- [x] `POST` с `tags: ["  Работа ", "работа", "Work"]` возвращает `201`
